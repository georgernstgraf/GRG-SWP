Lektion KM5-03 · OO-Fundament

Interfaces als Vertrag

„Egal was du bist — wenn du compareTo kannst, bin ich mit dir im Geschäft." Ein Vertrag über was, nie über wie.

Lektüre (Pflicht)

TypeScript Handbook: Interfaces und danach Type Compatibility (structural typing).

Einstiegsfrage

Wir wollen aus einer Liste das größte Element finden. Die Liste enthält Konten, Produkte, irgendetwas — die Funktion soll das gar nicht wissen müssen. Was muss ein Element mitbringen, damit „größer" überhaupt einen Sinn hat?

Ziel-Artefakt

function groesstes<T extends Comparable<T>>(liste: T[]): T | undefined {
  // kennt Konten, Produkte, … nicht — nur den Vertrag compareTo
}

Eine einzige Funktion für beliebige Typen — weil sie nur an einem Vertrag hängt, nicht an einer Klasse.

Vertrag über Handlung, nicht über Herkunft

// Der Vertrag: „Wer diesen Typ überreicht bekommt, kann compareTo rufen."
export interface Comparable<T> {
  compareTo(other: T): number;   // <0: dieses kleiner · 0: gleich · >0: größer
}

// Die Klasse unterzeichnet — und verspricht damit eine Implementierung
export class Sparkonto implements Comparable<Sparkonto> {
  compareTo(other: Sparkonto): number {
    return this.stand - other.stand;
  }
}

compareTo sagt nichts darüber, wie verglichen wird — Sparkonto vergleicht nach Kontostand, ein Produkt nach Preis. Der Vertrag ist gleich, die Umsetzung je Klasse anders. Das ist „was, nicht wie".

Warum mehrere Interfaces statt alles in eine Basisklasse packen?

Mehrere Verträge, eine Klasse

Vererbung (nächste Einheit) ist eine is-a-Beziehung mit einem Elternteil. Interfaces sind Verträge — und eine Klasse darf beliebig viele unterschreiben:

export interface Verzinsbar {
  jahresZins(): number;
}

// implements: zwei Verträge gleichzeitig
export class Sparkonto implements Comparable<Sparkonto>, Verzinsbar { … }

Sparkonto ist ein Konto — und es ist vergleichbar und verzinsbar. Fähigkeiten hängen an Interfaces, Abstammung an Vererbung. Wer beides vermischt, baut später beim O/R-Mapping (Verbund, SS) Schiffbruch.

Was ein Interface beschreiben kann

export interface Produkt {
  readonly id: string;        // Pflicht-Eigenschaft, nicht neu zuweisbar
  preis: number;              // Pflicht-Eigenschaft
  rabatt?: number;            // optionale Eigenschaft
  istVerfuegbar(): boolean;   // Pflicht-Methode
  versende(an: string): void; // Pflicht-Methode
}

? markiert optional: nicht jedes Produkt muss einen Rabatt haben. readonly im Interface heißt: Wer den Vertrag erfüllt, darf die Eigenschaft nach dem Entstehen nicht neu zuweisen.

Was bedeutet rabatt?: number im Interface?

Faustregel: Formen/Verträge als interface, komplexe Typ-Algebren (Union, Tupel) als type.

Structural typing — die TS-Eigenart

const testkonto = { jahresZins: () => 0.01 };  // kein implements, keine class
const v: Verzinsbar = testkonto;                // ok — die Form stimmt

Wer die geforderten Mitglieder hat, erfüllt den Vertrag — die Dekoration (implements) ist Dokumentation, nicht Bedingung. Java würde hier nein sagen; TypeScript sagt ja, solange die Form passt.

Was prüft TypeScript bei einer Interface-Zuweisung?

Verträge als Funktionsparametertypen

// Die Funktion kennt nur den Vertrag — jede erfüllende Klasse fliegt durch
function groesstes<T extends Comparable<T>>(liste: T[]): T | undefined {
  if (liste.length === 0) return undefined;
  let bestes = liste[0];
  for (const kandidat of liste) {
    if (kandidat.compareTo(bestes) > 0) bestes = kandidat;
  }
  return bestes;
}

groesstes([k1, k2, k3]);   // Sparkonto[] — solange sie Comparable<Sparkonto> sind

groesstes weiß nicht einmal, dass es Konten gibt. Deshalb Interfaces: Code, der an Verträgen hängt, bleibt erweiterbar, ohne angefasst zu werden — die stille Vorwegnahme des Open-Closed-Prinzips.

Warum steht in groesstes<T extends Comparable<T>> ein extends?

Jetzt du!

Erst vorhersagen, dann prüfen.

  1. Vorhersage: Eine Klasse deklariert implements Verzinsbar, vergisst aber jahresZins(). Kompiliert das — und wo genau meckert TypeScript?
  2. Vorhersage: Du weist ein Objekt mit jahresZins, aber ohne implements einer Variablen vom Typ Verzinsbar zu. Erlaubt oder nicht?
  3. Ausführen: Definiere Versendbar mit versende(an: string): void. Gib einer Klasse beide Verträge (Comparable<T> und Versendbar) und nutze sie als Parameter von groesstes(). Tests (rot → grün).

Typische Fehler

FehlerWas wirklich passiert
„Eine Klasse erbt von einem Interface" Interfaces werden implementiert, nicht vererbt: Fähigkeit (kann) statt Abstammung (ist ein).
Zur Laufzeit mit instanceof auf ein Interface prüfen Interfaces existieren zur Laufzeit nicht — sie sind reine Typ-Information. Dafür braucht es eine Unterscheidung über Felder/Methoden.
Signatur weicht minimal ab (anderer Parametertyp) Der Vertrag ist dann nicht erfüllt — implements erzwingt die exakte Form.
Alles in any stecken, „damit es läuft" Damit ist der Vertrag wertlos — genau die Typprüfung, die die Erweiterbarkeit sichert, ist abgeschaltet.

Aufgabe

Entwirf einen eigenen Vertrag mit mindestens einer Methode und einer readonly-Eigenschaft. Lass zwei verschiedene Klassen ihn unterschiedlich umsetzen, schreibe eine Funktion, die nur den Vertragstyp kennt (als Parameter), und zeige an beiden Klassen denselben Aufruf. Sichere das Verhalten mit Tests (rot → grün). Abgabe nach Vorgabe deiner Lehrperson.
