Lektion KM6-06 · Architektur

Schichtentrennung in einer Applikation

Datenbank, Service, Controller, Endpoints — und die eine Regel, die alles zusammenhält: Abhängigkeiten zeigen nach innen.

Lektüre (Pflicht)

Martin Fowler: PresentationDomainDataLayering — die klassischen Schichten und warum sie sich nicht kennen sollen. Dazu Hono: Routing und Hono: Context (c.req.json(), c.req.param(), c.json()) sowie Deno: Deno.serve.

Einstiegsfrage

Eine kleine Bank-App funktioniert. Alles steckt in einem Handler:

app.post("/api/ueberweisung", async (c) => {
  const { von, an, betrag } = await c.req.json();
  const quelle = db.query("SELECT * FROM konten WHERE iban = ?", [von]);
  const ziel   = db.query("SELECT * FROM konten WHERE iban = ?", [an]);
  if (betrag > quelle.stand) return c.json({ fehler: "keine Deckung" }, 409);
  db.query("UPDATE konten SET stand = stand - ? WHERE iban = ?", [betrag, von]);
  db.query("UPDATE konten SET stand = stand + ? WHERE iban = ?", [betrag, an]);
  return c.json({ ok: true });
});

Läuft. Aber: Wo änderst du etwas, wenn die Spalte stand künftig saldo heißt? Wo testest du die Regel „keine Deckung", ohne eine echte Datenbank und einen echten HTTP-Server zu starten? Und wer verhindert, dass zwei Entwickler:innen gleichzeitig dieselbe Datei umbauen? Genau dagegen hilft Schichtentrennung.

Ziel-Artefakt

Aus einem Handler werden fünf klar getrennte Bausteine — jeder mit genau einer Aufgabe:

SchichtAufgabedarf nichts wissen von …
Viewanzeigen, Eingaben einsammelnDB, Fachregeln
EndpointRoute + HTTP (Status, JSON)Fachregeln, DB
ControllerEin-/Ausgabe übersetzen, Fehler abfangenHTTP-Statuscodes, DB
ServiceGeschäftslogik / Ablauf (Use-Case)HTTP, konkrete DB
Repository (DB-Layer)laden/speichern, TransaktionFachregeln, HTTP

Und daneben, im Zentrum: die Domäne (Konto) aus KM5 — die reine Fachklasse mit ihren Invarianten.

Der Merksatz dieser Doppelstunde:

View → Endpoint → Controller → Service → Repository → DB
                        ↘      Domäne      ↙
Pfeile zeigen NACH INNEN — außen kennt innen, innen kennt außen nicht.

Leitregel: Abhängigkeiten zeigen nach innen

Eine Schicht darf die nächste aufrufen — nie zurück und nie quer. Der Service kennt das Repository nur als interface, nicht die konkrete Datenbank. Genau deshalb kann InMemoryKontoRepository im Unterricht und PrismaKontoRepository (mit INFI) in echt dieselbe Stelle besetzen.

Das ist dieselbe Idee wie in KM5: Ein Interface legt „was" fest, nicht „wie". Hieß es dort Comparable, heißt es hier KontoRepository.

Schicht 1 — Datenbank-Layer (Repository)

Er kann zwei Dinge: Objekte finden und speichern. Sonst nichts. Und er gibt Domänenobjekte zurück, keine Datenbank-Zeilen.

// repository/konto_repository.ts — der Vertrag, keine Implementierung
import { Konto } from "../domain/konto.ts";

export class KontoNichtGefundenError extends Error {}

export interface KontoRepository {
  finde(iban: string): Promise<Konto>;
  speichere(konto: Konto): Promise<void>;
  // atomar: alle Schreibvorgänge in fn — ganz oder gar nicht (siehe „Atomarität")
  transaktion<T>(fn: () => Promise<T>): Promise<T>;
}
// repository/in_memory_konto_repository.ts — Implementierung für Unterricht & Tests
export class InMemoryKontoRepository implements KontoRepository {
  private konten = new Map<string, Konto>();

  async finde(iban: string): Promise<Konto> {
    const konto = this.konten.get(iban);
    if (!konto) throw new KontoNichtGefundenError(`Konto ${iban} nicht gefunden`);
    return konto;
  }

  async speichere(konto: Konto): Promise<void> {
    this.konten.set(konto.iban, konto);
  }
  // transaktion() folgt im Abschnitt „Atomarität".
}

Wichtig: Die Fachregel „keine Deckung" steht hier nicht. Der DB-Layer weiß nicht, was ein Konto fachlich darf — er weiß nur, wie es in den Speicher kommt.

Wofür ist der Datenbank-Layer (Repository) zuständig?

Schicht 2 — Service-Layer

Hier lebt der Ablauf (Use-Case) „Geld überweisen". Der Service kennt die Domäne und das Repository-Interface — aber kein Hono, kein SQL, kein HTTP.

// service/konto_service.ts
export class KontoService {
  constructor(private repo: KontoRepository) {}

  async ueberweise(von: string, an: string, betrag: number): Promise<void> {
    const quelle = await this.repo.finde(von);
    const ziel   = await this.repo.finde(an);
    quelle.abheben(betrag);   // Domänenregel aus KM5: wirft bei fehlender Deckung
    ziel.einzahlen(betrag);
    await this.repo.speichere(quelle);
    await this.repo.speichere(ziel);
  }

  async stand(iban: string): Promise<number> {
    return (await this.repo.finde(iban)).stand;
  }
}

Die Invarianten aus KM5 sind hier gratis: abheben prüft die Deckung, einzahlen weist negative Beträge ab. Der Service verlässt sich darauf — er prüft nicht doppelt.

Was darf der Service-Layer nicht wissen?

Schicht 3 — Controller

Der Controller ist der Übersetzer: Er nimmt die nackten Daten aus der Außenwelt (z. B. ein JSON-Objekt), ruft den Service und übersetzt Ergebnis bzw. Fehler in eine neutrale Form. Er kennt keine HTTP-Statuscodes — die sind Sache des Endpoints.

// controller/konto_controller.ts
export type FehlerArt = "nicht_gefunden" | "keine_deckung" | "ungueltig";

export type Ergebnis<T> =
  | { ok: true; wert: T }
  | { ok: false; art: FehlerArt; meldung: string };

export class KontoController {
  constructor(private service: KontoService) {}

  async ueberweisung(daten: UeberweisungsDaten): Promise<Ergebnis<null>> {
    try {
      await this.service.ueberweise(daten.von, daten.an, daten.betrag);
      return { ok: true, wert: null };
    } catch (fehler) {
      return { ok: false, ...this.art(fehler) };   // Fehler-Thread
    }
  }

  private art(fehler: unknown): { art: FehlerArt; meldung: string } {
    if (fehler instanceof KontoNichtGefundenError) {
      return { art: "nicht_gefunden", meldung: fehler.message };
    }
    if (fehler instanceof KeineDeckungError) {
      return { art: "keine_deckung", meldung: fehler.message };
    }
    return { art: "ungueltig", meldung: (fehler as Error).message };
  }
}

Damit ist der Fehler-Thread sichtbar: Die Domäne wirft eine typisierte Fehlerklasse, der Service reicht sie durch, der Controller übersetzt sie in FehlerArt — und erst der Endpoint macht daraus einen HTTP-Status. Jede Schicht kennt nur ihr eigenes Vokabular.

Wozu ist der Controller da?

Schicht 4 — Endpoints

Der Endpoint ist dünn. Er kennt die Route und die HTTP-Sprache — sonst nichts. Hono erledigt das Auslesen von Body und Parametern:

// routes/konto_routes.ts
const STATUS: Record<FehlerArt, 400 | 404 | 409> = {
  nicht_gefunden: 404,
  keine_deckung: 409,
  ungueltig: 400,
};

app.post("/api/ueberweisung", async (c) => {
  const daten = await c.req.json<UeberweisungsDaten>();
  const ergebnis = await controller.ueberweisung(daten);
  if (ergebnis.ok) return c.json({ ok: true });
  return c.json({ ok: false, fehler: ergebnis.meldung }, STATUS[ergebnis.art]);
});

app.get("/api/konten/:iban", async (c) => {
  const ergebnis = await controller.stand(c.req.param("iban"));
  if (ergebnis.ok) return c.json({ iban: c.req.param("iban"), stand: ergebnis.wert });
  return c.json({ ok: false, fehler: ergebnis.meldung }, STATUS[ergebnis.art]);
});

c.req.json<T>() liest den Request-Body typisiert, c.req.param("iban") holt den Pfadparameter, c.json(...) setzt Antwort und Status. Der Endpoint entscheidet nur, dass ein nicht_gefunden zu 404 wird — nicht, wann es auftritt.

Und Deno Desktop? Dort gilt dieselbe Rollenverteilung: Die Bindings (bindings.ueberweise(...)) sind der Controller, das Webview ist die View, und Deno.serve ist der Unterbau, auf dem Hono (oder die Route) läuft.

Was gehört in die Endpoint-Schicht?

Schicht 5 — View

Die View ist das Webview (HTML/CSS aus Jg II). Sie soll dumm bleiben: anzeigen und Eingaben einsammeln — nicht rechnen.

<!-- static/index.html -->
<form id="ueberweisung">
  <input name="von" placeholder="Von (IBAN)">
  <input name="an"  placeholder="An (IBAN)">
  <input name="betrag" type="number">
  <button>Überweisen</button>
</form>

<script>
  form.addEventListener("submit", async (e) => {
    e.preventDefault();
    const daten = Object.fromEntries(new FormData(form));
    const antwort = await fetch("/api/ueberweisung", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(daten),
    });
    zeigeStatus(await antwort.json());   // die View zeigt nur an
  });
</script>

Kein if (betrag > stand) in der View — das wäre die Fachregel an der falschen Stelle. Der Datenfluss läuft einmal nach unten (View → … → DB) und als Ergebnis wieder nach oben.

Was ist die Aufgabe der View?

Atomarität — ganz oder gar nicht

Schau auf ueberweise(): Es speichert zweimal — erst die Quelle, dann das Ziel. Was, wenn der zweite speichere abbricht (Netz, DB weg)?

await this.repo.speichere(quelle);   // ✓ AT01: 100 → 70 (schon persistiert!)
await this.repo.speichere(ziel);     // ✗ Absturz — nie ausgeführt

Ergebnis: 30 € sind verschwunden. Geld darf so etwas nicht. Die beiden Schreibvorgänge müssen ein unteilbarer Schritt sein — eine Transaktion.

Wichtig: Das ist Aufgabe des DB-Layers, nicht des Services. Der Service sagt „diese Arbeit gehört zusammen", die Datenbank garantiert es. Für die In-Memory-Variante heißt das: Zustand sichern und bei Fehler zurückrollen.

// service/konto_service.ts — der Ablauf wird in eine Transaktion geklammert
await this.repo.transaktion(async () => {
  const quelle = await this.repo.finde(von);
  const ziel   = await this.repo.finde(an);
  quelle.abheben(betrag);
  ziel.einzahlen(betrag);
  await this.repo.speichere(quelle);
  await this.repo.speichere(ziel);
});
// in_memory_konto_repository.ts — Rollback über eine Sicherungskopie
async transaktion<T>(fn: () => Promise<T>): Promise<T> {
  const sicherung = new Map<string, Konto>();
  for (const [iban, konto] of this.konten) sicherung.set(iban, konto.kopie());
  try {
    return await fn();
  } catch (fehler) {
    this.konten = sicherung;   // Rollback: alles zurück auf Anfang
    throw fehler;
  }
}

Mit Prisma (Verbund) übernimmt das die Datenbank: prisma.$transaction(async (tx) => { … }). Der Service-Code bleibt fast gleich — nur transaktional. Genau das ist der Wert der Schichtentrennung: Die Fachlogik hängt nur am Repository-Interface, nicht an SQLite.

Warum muss die Überweisung in einer Transaktion laufen?

Verzeichnislayout — wo liegt was?

Die Schichten aus dem Code sollen sich im Ordnerbaum wiederfinden:

meine-app/
├── deno.json
├── main.ts                     # Composition Root: verdrahtet alle Schichten
├── src/
│   ├── domain/
│   │   └── konto.ts            # Fachklasse (KM5), DB- und HTTP-frei
│   ├── repository/
│   │   ├── konto_repository.ts        # Interface + Fehlerklassen
│   │   └── in_memory_konto_repository.ts
│   ├── service/
│   │   └── konto_service.ts
│   ├── controller/
│   │   └── konto_controller.ts
│   └── routes/
│       └── konto_routes.ts     # Hono-Endpoints
├── static/
│   └── index.html              # View (Webview)
├── tests/                      # oder *_test.ts direkt neben dem Code
│   └── konto_service_test.ts
└── prisma/                     # ab Verbund/INFI: Schema + Migrationen
    └── schema.prisma

Allgemeine Tipps:

  • Composition Root: main.ts ist der einzige Ort, der alle Schichten kennt und mit new verdrahtet. Überall sonst gilt: nur die nächste Schicht importieren.
  • Eine Richtung: routes → controller → service → repository. Kommt ein Import in die Gegenrichtung oder quer vor, ist die Schicht „undicht".
  • Technik- vs. feature-orientiert: Für kleine Apps sind Technik-Ordner (domain/, service/ …) ideal. Wächst die App, gruppiert man nach Feature (src/konto/…, src/kunde/…) und behält die Schichten innerhalb des Features.
  • Tests spiegeln die Struktur: Der Service ist ohne Server und ohne echte DB testbar, weil er am Interface hängt (In-Memory-Repository).
  • Konfiguration zentral: Port, DB-URL usw. an einer Stelle (config.ts, .env), nicht verstreut.
  • Anti-Tipps: Riesen-utils/, in das alles wandert; zirkuläre Importe; Logik im Controller; dieselbe Aufgabe in zwei Schichten; „Schicht" nur als Ordner ohne Regel.

Was besagt die Dependency Rule?

Jetzt du!

Erst vorhersagen, dann prüfen.

  1. Vorhersage: Du änderst im DB-Schema stand in saldo. Wie viele Dateien außerhalb des Repository-Ordners musst du anfassen? Begründe.
  2. Vorhersage: Jemand ruft controller.ueberweisung(...) mit einem negativen Betrag auf. Welche Schicht wirft, und in welchen HTTP-Status mündet es später?
  3. Ausführen: Zerlege den Handler aus der Einstiegsfrage in die fünf Schichten. Schreibe einen Test für den Service, der ohne HTTP-Server läuft (In-Memory-Repository). Rot → grün.

Typische Fehler

FehlerWas wirklich passiert
Fachregel im Controller oder Endpoint Die Regel ist versteckt oder doppelt — Domäne bzw. Service ist die richtige Stelle.
Service importiert Hono oder Prisma Die Schicht ist undicht: Tests brauchen plötzlich Server/DB, der Austausch (In-Memory ↔ Prisma) wird unmöglich.
Repository gibt DB-Zeilen statt Domänenobjekte Fachregeln fehlen, das Domänenmodell wird umgangen — der Kern von KM5 geht verloren.
Zwei Schreibvorgänge ohne Transaktion Ein halber Zustand bleibt persistiert (z. B. Geld verschwindet).
Endpoint ruft das Repository direkt Schicht übersprungen: Controller und Service (Regeln, Übersetzung) werden umgangen.
Jede Mini-Funktion in eine eigene Schicht pressen Over-Engineering: Schichten sollen Änderungen isolieren, nicht das Denken ersetzen.

Zusammenfassung

SchichtAufgabe in einem Satz
ViewAnzeigen, Eingaben einsammeln — keine Logik.
EndpointRoute + HTTP: Body/Parameter lesen, Status/JSON setzen.
ControllerÜbersetzen und Fehler abfangen — ohne HTTP-Status.
ServiceGeschäftsablauf (Use-Case) — ohne DB- und HTTP-Kenntnis.
RepositoryLaden/Speichern und Transaktionen — ohne Fachregel.
DomäneDie Regeln selbst (Konto-Invarianten aus KM5).

Ausblick: Die KM5-03-Idee „Vertrag, nicht Umsetzung" wird hier zur Architektur: Der Service hängt am KontoRepository-Interface. Ab dem Repository-Pattern (UE 5) und im INFI-Verbund liefert die Prisma-Implementierung genau diesen Vertrag — eine Datei, zwei Fächer.

Aufgabe

Zerlege den monolithischen Handler aus der Einstiegsfrage (oder einen eigenen) in die fünf Schichten: Domäne, Repository (Interface + In-Memory-Implementierung), Service, Controller, Endpoint. Halte das Repository hinter einem Interface, sodass die Datenbank austauschbar bleibt. Schreibe einen Test für den Service, der ohne HTTP-Server und ohne echte Datenbank läuft (rot → grün). Weise die Fehlerkette nach: Ein Domänenfehler führt über den Controller zu einem passenden HTTP-Status (404 bzw. 409). Abgabe nach Vorgabe deiner Lehrperson.
