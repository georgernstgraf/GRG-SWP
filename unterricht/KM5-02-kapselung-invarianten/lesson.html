Kapselung & Invarianten

Die Klasse wird Herrin ihres Zustands: Sichtbarkeiten, kontrollierte Türen und Fail-Fast — damit ungültige Objekte gar nicht erst entstehen.

Lektüre (Pflicht)

TypeScript Handbook: Classes — Abschnitte public/private/protected, readonly, Accessors. Ergänzend MDN: Private properties für #feld.

Einstiegsfrage

const k = new Konto("AT1", 500);
k.kontostand = -1_000_000;   // kompiliert, wenn kontostand public ist — und ist Datenmüll

Die Klasse verspricht „ein Konto hat einen sinnvollen Kontostand" — aber jeder Zugriff von außen kann das Versprechen brechen. Wer darf diesen Zustand eigentlich ändern? Und wie erzwingt man das, statt es nur zu hoffen?

Ziel-Artefakt

Am Ende dieser Doppelstunde steht eine Konto-Klasse, die beweisbar (durch Tests) garantiert: kein ungültiges Objekt wird je geboren, keine Methode bricht die Regel. Das ist der Übergang von „Code läuft" zu „Code ist vertrauenswürdig".

Das Problem: unkontrollierter Zustand

Sobald Müll einmal drin ist, verteilt er sich über das ganze Programm — jene Fehler, die man drei Wochen später in einer völlig anderen Datei sucht. Kapselung ist die Antwort: Der Zustand gehört der Klasse, die ihn schützt.

Die Lösung in drei Schichten

Schicht Werkzeug Wirkung
1. Sichtbarkeiten private / readonly Kein Zugriffspfad von außen; Identität unveränderlich
2. Kontrollierte Türen getter / setter, Methoden mit Prüfung Jede Änderung geht durch die Prüfung
3. Fail-Fast throw im Konstruktor & in Methoden Ungültige Werte sterben sofort, nicht drei Wochen später

Warum hat kontostand in einer gepflegten Klasse keinen setter?

Sichtbarkeiten: public, private, protected, readonly

ModifiziererWer darf zugreifen?Typischer Einsatz
public (Default)alleMethoden, die die Welt braucht
privatenur dieselbe Klasseinterne Feldwerte, Hilfsmethoden
protecteddieselbe Klasse und SubklassenZustand, den eine Subklasse erben soll (ab Vererbung)
readonlyalle lesen, nur der Konstruktor schreibenIdentität (IBAN, ID)

TypeScript-Eigenart: private prüft nur die Kompilierzeit — zur Laufzeit bleibt das Feld erreichbar. Willst du harte Kapselung im JavaScript selbst, nutzt du #feld:

class Konto {
  #kontostand = 0;        // echtes JS-private: von außen unerreichbar
  readonly iban: string;  // TS-readonly: nur im Konstruktor setzbar
  // …
}

Worin unterscheiden sich private kontostand (TS) und #kontostand (JS)?

Invarianten & Fail-Fast

Invariante = eine Regel, die für jedes Objekt zu jedem Zeitpunkt gilt. Der Konstruktor sichert sie beim Entstehen, jede zustandsändernde Methode beim Wachsen.

export class Sparkonto {
  private kontostand: number;

  constructor(kontostand: number) {
    // Fail-Fast: ein Sparkonto wird NIE negativ geboren
    if (kontostand < 0) {
      throw new Error(`Kontostand darf nicht negativ sein (war ${kontostand})`);
    }
    this.kontostand = kontostand;
  }

  // getter: Lesen ist unproblematisch — Zugriff, keine Änderung
  get stand(): number {
    return this.kontostand;
  }

  // Änderung nur über geprüfte Methoden — kein setter für kontostand
  einzahlen(betrag: number): void {
    if (betrag <= 0) throw new Error("Betrag muss positiv sein");
    this.kontostand += betrag;
  }
}

Fauler Code „rechnet einfach los" (Happy Path) und lässt den Fehler irgendwann unten aufschlagen. Fail-Fast wirft beim ersten unmöglichen Aufruf. Der Unterschied ist nicht Stil: „Fehler in 2 Sekunden mit präziser Meldung" gegen „Fehler in 3 Wochen ohne Spur".

Wo gehört die Prüfung betrag > 0 hin?

Mehrere Invarianten an einer Klasse

export class Konto {
  private kontostand: number;
  constructor(start: number) {
    if (start < 0) throw new Error("Start negativ");
    this.kontostand = start;
  }
  abheben(betrag: number): void {
    if (betrag <= 0) throw new Error("Betrag muss positiv sein");
    if (betrag > this.kontostand) throw new Error("Kein Dispo vereinbart");
    this.kontostand -= betrag;   // Invariante: kontostand bleibt ≥ 0
  }
}

Zwei Regeln, zwei Prüfungen, eine Methode: positiv und gedeckt. Jede Verletzung endet sofort — bevor ein halb-verändertes Objekt zurückbleibt.

Was bedeutet „fail-fast" bei abheben() genau?

Jetzt du!

Erst vorhersagen, dann prüfen.

  1. Vorhersage: Ein public kontostand und ein private kontostand — bei welchem der beiden schlägt deno check auf k.kontostand = -1 fehl? Und was passiert jeweils zur Laufzeit?
  2. Vorhersage: Ein Konstruktor wirft bei negativem Startwert. Wie viele Objekte existieren nach new Konto(-5) — null oder ein halbfertiges? Begründe.
  3. Ausführen: Erweitere Konto um ueberweisen(auf: Konto, betrag), sodass entweder beide Konten stimmen oder gar keines. Sichere es mit Tests (rot → grün).

Typische Fehler

FehlerWas wirklich passiert
Feld public lassen, „ist ja nur ein Demo" Jeder Aufrufer kann die Invariante brechen; die Fehlersuche wandert Wochen später in eine fremde Datei.
setter bauen, der die Prüfung umgeht Öffnet genau die zweite Tür, die man schließen wollte — die Invariante ist dahinter wertlos.
getter mit Seiteneffekt (z. B. „Zinsen buchen") Lesen soll den Zustand nicht ändern. Zustandsänderung gehört in eine benannte Methode.
Konstruktor prüft, Methoden nicht Kapselung ist eine permanente Regel, nicht eine einmalige Eingangskontrolle.

Ausblick: In KM5-03 machen wir aus Verhalten einen Vertrag (interface) — und ab der Vererbung wird protected wichtig, weil Subklassen den geschützten Zustand erben.

Aufgabe

Nimm eine kleine Klasse deiner Wahl mit mindestens einem veränderlichen Feld. Formuliere zwei Invarianten, sichere sie mit Fail-Fast im Konstruktor und in jeder mutierenden Methode, und schreibe zu jeder Invariante einen Test, der beweist, dass die Verletzung wirklich wirft (rot → grün).
