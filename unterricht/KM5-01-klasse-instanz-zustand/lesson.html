Lektion KM5-01 · OO-Fundament

Klasse, Instanz, Zustand — formalisiert

Der Bauplan, die Objekte und ihr Zustand: warum zwei Konten mit demselben Kontostand trotzdem zwei verschiedene Dinge sind.

Lektüre (Pflicht)

MDN: JavaScript Classes — lies die Abschnitte constructor und Instanzfelder. Du kannst Klassen schon schreiben; hier schärfen wir die Begriffe dahinter.

Einstiegsfrage

Zwei Konten im Speicher:

const a = new Konto("AT12…01", 500);
const b = new Konto("AT12…01", 500);

Sind a und b dasselbe Konto? Beide tragen dieselbe IBAN und denselben Kontostand. Die Antwort ist trotzdem nein — und der Grund dafür ist der ganze Stoff dieser Lektion.

Warum der Bruch nicht mehr reicht

class Bruch hat zwei Felder und eine Rechenart. Das genügt, um Syntax zu lernen — aber nicht, um über Design zu sprechen. Ein Konto hat Identität (die IBAN macht das Konto einzigartig), Zustand, der sich ständig ändert (der Kontostand), und Regeln, die niemals verletzt werden dürfen. Genau diese drei Dinge machen OO-Denken aus.

Die drei Begriffe, sauber getrennt

Begriff Antwortet auf die Frage Am Konto
Klasse Wie bauen wir? class Konto — der Bauplan, existiert einmal
Instanz / Objekt Was existiert jetzt? new Konto("AT12…", 500) — jedes new erzeugt ein neues Ding
Zustand Welche Werte hält dieses Ding gerade? kontostand = 750 — der Feldwert dieser Instanz
Identität — der vierte Begriff

Ein Konto ist einzigartig, auch wenn zwei Konten denselben Kontostand haben. === vergleicht Identität (gleicher Speicherplatz); ein selbst geschriebenes equals() vergleicht Zustand.

Zustand live: Feldwerte sind pro Instanz

export class Konto {
  private kontostand: number;   // Zustand — gehört nur dieser Instanz
  readonly iban: string;        // Identität — nach dem Konstruktor unveränderlich

  constructor(iban: string, startBetrag: number) {
    this.iban = iban;
    this.kontostand = startBetrag;
  }

  einzahlen(betrag: number): void {
    this.kontostand += betrag;  // ändert den Zustand DIESER Instanz
  }

  equals(other: Konto): boolean {
    return this.iban === other.iban;
  }
}

Ändert k1.einzahlen(100), bleibt k2 unberührt. Das ist der ganze Punkt: Zustand lebt pro Instanz, Verhalten teilt sich über die Klasse.

Zwei Konten: a = new Konto("AT1", 500), b = new Konto("AT1", 500). Was gilt?

Was verändert einzahlen()?

Jetzt du!

Erst vorhersagen, dann prüfen.

  1. Vorhersage: const c = a; — gilt c === a? Wie viele Konto-Objekte gibt es jetzt, wie viele Variablen?
  2. Vorhersage: Wir rufen a.einzahlen(100) und lesen danach c.kontostand. Was steht dort — 500 oder 600? Warum?
  3. Ausführen: Schreibe equals() so, dass zwei Konten mit gleicher IBAN als gleich gelten — egal, wie unterschiedlich der Kontostand ist. Prüfe mit zwei Deno.test-Fällen (gleich / ungleich).

Typische Fehler

FehlerWas wirklich passiert
a === b für „gleiches Konto" halten === vergleicht Identität, nicht Zustand. Zwei neue Konten sind nie ===. Zustandsvergleich braucht equals().
„Die Methode ändert die Klasse" Methoden ändern nie den Bauplan — nur die Feldwerte einer Instanz (this).
readonly mit „konstant" verwechseln readonly verbietet nur die Neuzuweisung nach dem Konstruktor — es ist kein const für Objekte.

Dein Win heute

Du kannst zu jedem Code sagen: Das ist Bauplan, das ist eine Instanz, das ist Zustand, das ist Identität — und begründen, warum equals() etwas anderes tut als ===. Diese Unterscheidung trägt das gesamte Semester (Kapselung, Vererbung, Polymorphismus bauen alle darauf auf).
