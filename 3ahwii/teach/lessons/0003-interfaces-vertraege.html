Interfaces als Vertrag

Bislang haben Klassen gesagt: „Ich bin ein Sparkonto." Heute drehen wir es um: „Egal was du bist — wenn du compareTo kannst, bin ich mit dir im Geschäft." Ein interface ist ein Vertrag über was, nie über wie.

Vertrag über Handlung, nicht über Herkunft

// Der Vertrag: „Wer diesen Typ überreicht bekommt, kann compareTo rufen."
export interface Comparable<T> {
  compareTo(other: T): number;   // <0: dieses kleiner · 0: gleich · >0: größer
}

// Die Klasse unterzeichnet — und verspricht damit eine Implementierung
export class Sparkonto implements Comparable<Sparkonto> {
  // …Zustand wie in Lesson 2…
  compareTo(other: Sparkonto): number {
    return this.kontostand - other.kontostand;
  }
}

Wichtig: compareTo sagt nichts darüber, wie verglichen wird — Sparkonto vergleicht nach Kontostand, dein Produkt nach Preis. Der Vertrag ist gleich, die Umsetzung je Klasse anders. Das ist „was, nicht wie".

Mehrere Verträge, eine Klasse

Vererbung (nächste Woche) ist eine is-a-Beziehung mit einem Elternteil. Interfaces sind Verträge — und eine Klasse darf beliebig viele unterschreiben: 

export interface Verzinsbar {
  jahresZins(): number;
}

// implements: zwei Verträge gleichzeitig
export class Sparkonto implements Comparable<Sparkonto>, Verzinsbar { … }

Sparkonto ist ein Konto — und es ist vergleichbar und verzinsbar. Fähigkeiten hängen an Interfaces, Abstammung an Vererbung. Wer beides vermischt, baut später beim O/R-Mapping (Verbund, SS) Schiffbruch.

Warum mehrere Interfaces statt alles in die Basisklasse packen?

Ein Konto ist ein Konto (Vererbung) — aber vergleichbar zu sein und verzinsbar zu sein sind unabhängige Fähigkeiten, die auch andere Klassen haben können.

Structural typing — die TS-Eigenart

TypeScript prüft die Form, nicht die Unterschrift:

const testkonto = { jahresZins: () => 0.01 };   // kein implements, keine class
const v: Verzinsbar = testkonto;   // ok — die Form stimmt, TS zufrieden

Wer die geforderten Mitglieder hat, erfüllt den Vertrag — Dekoration (implements) ist Dokumentation, nicht Bedingung. Das nennt man structural typing. Java würde hier nein sagen; TS sagt ja, solange die Form passt.

Was prüft TypeScript bei einer Interface-Zuweisung?

Structural typing: die Struktur zählt. implements hilft dem Compiler und dem Leser, aber die Zuweisung hängt allein an der Form.

Verträge als Funktionsparametertypen

// Die Funktion kennt nur den Vertrag — jede erfüllende Klasse fliegt durch
function groesstes<T extends Comparable<T>>(liste: T[]): T | undefined {
  if (liste.length === 0) return undefined;
  let bestes = liste[0];
  for (const kandidat of liste) {
    if (kandidat.compareTo(bestes) > 0) bestes = kandidat;
  }
  return bestes;
}

groesstes([k1, k2, k3]);   // Sparkonto[] — solange sie Comparable<Sparkonto> sind

groesstes weiß nicht einmal, dass es Kontos gibt. Deshalb Interfaces: Code, der an Verträgen hängt, bleibt erweiterbar, ohne anzufassen zu werden — die stille Vorwegnahme des Open-Closed-Prinzips, das uns durchs ganze Semester begleitet.

Dein Win heute

Du deklarierst eigene Verträge, erfüllst mehrere davon pro Klasse, und schreibst Funktionen, die nur den Vertrag kennen. Der nächste Test, der nächste Subtyp, die nächste Domäne — alles passt durch dieselbe Tür.
