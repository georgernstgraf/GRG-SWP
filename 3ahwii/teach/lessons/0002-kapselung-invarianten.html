Kapselung & Invarianten

Letzte Woche haben wir das Konto gebaut — aber jeder kann kontostand = -1000000 schreiben, wenn das Feld öffentlich ist. Heute machen wir die Klasse zur Herrin ihres Zustands: Kapselung ist das Werkzeug, Invarianten das Ziel.

Das Problem: unkontrollierter Zustand

const k = new Konto("AT1", 500);
k.kontostand = -1_000_000;   // kompiliert, wenn kontostand public ist — und ist Datenmüll

Die Klasse verspricht „ein Konto hat einen sinnvollen Kontostand" — aber jeder Zugriff von außen kann das Versprechen brechen. Sobald der Müll einmal drin ist, verteilt er sich über das ganze Programm: jene Fehler, die man drei Wochen später in einer völlig anderen Datei sucht.

Die Lösung in drei Schichten

Schicht Werkzeug Wirkung
1. Sichtbarkeiten private / readonly Kein Zugriffspfad von außen; Identität unveränderlich
2. Kontrollierte Türen getter / setter, Methoden mit Prüfung Jede Änderung geht durch die Prüfung
3. Fail-Fast throw im Konstruktor & Methoden Ungültige Werte sterben sofort, nicht drei Wochen später 
export class Sparkonto {
  private kontostand: number;

  constructor(kontostand: number) {
    // Fail-Fast: ein Sparkonto wird NIE negativ geboren
    if (kontostand < 0) {
      throw new Error(`Kontostand darf nicht negativ sein (war ${kontostand})`);
    }
    this.kontostand = kontostand;
  }

  // getter: Lesen ist unproblematisch — Zugriff, keine Änderung
  get kontostand(): number {
    return this.kontostand;
  }

  // Änderung nur über geprüfte Methoden — kein setter für kontostand
  einzahlen(betrag: number): void {
    if (betrag <= 0) throw new Error("Betrag muss positiv sein");
    this.kontostand += betrag;
  }
}
Invariante = eine Regel, die für jedes Objekt zu jedem Zeitpunkt gilt. Konstruktor sichert sie beim Entstehen, jede zustandsändernde Methode hält sie beim Wachsen. Checkliste zum Abhaken →

Warum hat kontostand hier keinen setter?

Ein setter würde die zweite Tür aufmachen, durch die die Invariante verletzt werden kann. Änderungen nur über einzahlen()/abheben() — dort steht die Prüfung.

Fail-Fast vs. Happy Path — die Review-Frage

Fauler Code „rechnet einfach los" (Happy Path) und lässt den Fehler irgendwann unten aufschlagen. Fail-Fast wirft beim ersten unmöglichen Aufruf. Der Unterschied ist nicht Stil — er ist die Differenz zwischen „Fehler gefunden in 2 Sekunden mit präziser Meldung" und „Fehler gefunden in 3 Wochen ohne Spur".

Wo gehört die Prüfung betrag > 0 hin?

Die Klasse verteidigt ihre Invariante selbst, an jeder Tür, durch die Zustand entstehen oder sich ändern kann — nicht der Aufrufer draußen.

Dein Win heute

Du schreibst Klassen, die beweisbar (durch Tests) garantieren: kein ungültiges Objekt wird je geboren, keine Methode bricht die Regel. Das ist der Übergang von „Code läuft" zu „Code ist vertrauenswürdig".
