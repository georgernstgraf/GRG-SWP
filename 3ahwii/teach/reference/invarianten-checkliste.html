Invarianten-Checkliste

Wie du für jede Klasse deiner Domäne durchgehst, ob sie ihre Regeln wirklich garantiert. Anwenden auf jede HÜ-Klasse — und in der PLF auffindbar.

1. Regeln sammeln

Frage zu jedem Feld: Welche Werte sind sinnvoll, welche sind Datenmüll?

  • kontostand — darf nie unter −Überziehungsrahmen sinken.
  • gewicht (Tier) — muss > 0 sein.
  • kmStand (Fahrzeug) — darf nie sinken (readonly!), nur wachsen.
  • preis (Produkt) — ≥ 0; Nachkommastellen → Cent speichern.

2. Sichern — an genau einer Stelle

Wo? Wie? Regel
Konstruktor if (betrag <= 0) throw new Error(…) Ein Objekt wird nie ungültig geboren.
Methoden, die Zustand ändern Prüfung vor der Änderung (Fail-Fast) Keine Methode umgeht die Prüfung.
Setter (falls vorhanden) Nur mit Prüfung — oder gar kein Setter Setter ohne Prüfung = Kapselung zum Schein.
private + readonly Zustand unsichtbar, Identität unveränderlich Kein Zugriffspfad von außen bleibt offen.
Fail-Fast vs. Happy Path: Fail-Fast wirft sofort beim ungültigen Aufruf. Der Happy-Path-Ansatz „rechnen, irgendwann fällt es auf" schiebt denselben Fehler tiefer ins System — dort kostet er ein Vielfaches. Code-Review-Frage im Unterricht: Wo wird das hier falsch — und wann merkt es jemand?

3. Beweisen — mit Tests

Eine Invariante, die nicht getestet wird, ist eine Behauptung. Für jede Regel mindestens:

  • 1 gültiger Fall (Happy Path bleibt grün).
  • 1 Grenzfall exakt an der Grenze (betrag = 0, kontostand = −überzug).
  • 1 ungültiger Fall mit assertThrows — und die Fehlermeldung prüfen. 
Deno.test("new Sparkonto(-1) wirft — Invariante gesichert", () => {
  assertThrows(
    () => new Sparkonto(-1),
    Error,
    "negativ",
  );
});

4. Schnell-Check vor Abgabe

  • □ Alle Felder private (oder bewusst public mit Begründung)?
  • □ Identitätsfelder readonly?
  • □ Konstruktor prüft alle Invarianten?
  • □ Jede zustandsändernde Methode prüft zuerst?
  • □ Fehler mit sinnvoller deutscher Meldung (was ist falsch, was war erlaubt)?
  • □ Grenzfälle getestet, nicht nur Happy Path?
